# revision-retro — 檢討「為什麼改這麼多版」

> 位置：成品交付後或收尾時，回頭看流程。不是修文件本身，也不是 multi-work 的 Retro（那個檢討分工與 token）。

## 目的
同一份成品出到 v8、v17，代表每一版都有人覺得「還不對」。這個 skill 回答：
1. 每一版為什麼要改？
2. 哪些修改本來可以在 v1 之前問清楚或查清楚？
3. 下次怎麼一次做對？（給具體可採用的規則，不給泛泛的建議）

## 主動提醒
收尾（session wrap）時，若發現某成品已到 v5 以上，或一天內出了 3 版以上，用一行問使用者「要不要做版本檢討」。使用者同意才開始，不自動跑。

## 原則
- **先查證據，再問人。** 不一開始就丟一串問題給使用者；能從檔案和紀錄看出來的就自己看。
- **每一條結論標證據等級**：`[對話原文]`（引使用者原話與時間）、`[檔案差異]`（兩版比對所見）、`[追蹤檔]`（journal／progress／todo 的記載）、`[推論]`（我的判斷，沒有直接證據）。`[推論]` 不得寫成事實語氣。
- **不追究誰的錯**，只分類原因。「我（Claude）沒先確認」「我理解錯」是合法的原因類別，要誠實列出。
- **只讀不改**：本 skill 只寫檢討報告，不改成品、不改專案 claude.md 或其他 skill。要採用規則，使用者確認後才另行動手。
- **省 token**：對話紀錄用腳本過濾（時間窗＋專案資料夾），不整份讀；版本比對只抽文字，不貼整份內容。

## 流程

### 1. 鎖定對象
- 使用者指定的檔案或成品；沒指定就問一句（只問這個）。
- 列出版本：`python reference/collect_history.py <成品所在資料夾> <基底檔名>`
  輸出每版的修改時間、大小、與前一版的間隔。
  `<基底檔名>` 不要含 `_vN`（腳本用「檔名開頭相符」找版本，含 `_v1` 會連 `_v10`～`_v17` 一起抓到）。
- 先看形狀（不要急著下結論）：
  - 連續幾版間隔 <10 分鐘 → 多半是小修／對版面（找「樣式或格式」類原因）。
  - 一版間隔很長（數小時）後，檔案大小大幅變化 → 多半是新資料、新需求或審閱回饋。
  - 大小忽大忽小 → 內容被加了又刪（範圍或方向反覆）。
- **判斷成品類型**（影響後面怎麼歸因與給什麼建議）：
  - **交付型**：有固定的問題或規格要回答（例：回覆客戶的 7 個問題、審查報告）。版本多通常代表前期沒問清楚，可避免比例高。
  - **調查型**：邊量測、邊分析、邊更新結論（例：FACA、問題分析簡報）。版本多多半是新資料陸續到達，屬合理進展；
    重點不是減少版本，而是「結論／摘要頁是否與最新資料同步」。不要硬套「v1 前問清楚」。
  - 混合型就分段判斷。類型寫進報告摘要。

### 2. 蒐集證據（依序，夠了就停）
1. **對話紀錄**（最有價值）：
   `python reference/collect_history.py <資料夾> <基底檔名> --transcripts ~/.claude/projects/<該專案的資料夾> --window`
   `--window` 列出版本時間範圍內使用者說的所有話（使用者很少打檔名，所以用時間窗）。
   - 時間戳：對話紀錄是 UTC，檔案修改時間是本地時間（例：台灣差 8 小時）；腳本已換算，但手動對照版本與訊息時要自己加減。
   - 預設每則只印 300 字；關鍵訊息（起始請求、大幅改方向的意見）用 `--full-msgs N` 印出前 N 則全文。
   - `--handbacks`：一併印出時間窗內 subagent／reviewer 的回報全文（前 2500 字）。**reviewer 的發現是歸因的高價值證據**
     （例如哪些數字被審出錯誤、哪一版吸收了修正），務必讀。
   專案資料夾名稱是路徑把 `\`、`:` 換成 `-`（例：`D:\Work\ProjA` → `D--Work-ProjA`）。
   也可不加 `--window`，改用檔名關鍵字。結果太多時用 `--max-msgs` 限制，再針對版本間隔的時間點細看。
2. **版本差異**：加 `--diff`，腳本會逐版比對 pptx／xlsx／docx，輸出頁數（投影片／工作表／每 20 段）、圖片數、有幾頁內容變動、新增幾頁；空白差異已忽略。
   讀法：`changed=0` 但出了新版 → 只有格式或版面變動；`changed` 接近全部 → 整份重寫或全域修改（常是規範或用語統一）；
   `added` 持續增加 → 範圍擴張。文字類（md／html／py）直接 diff。缺套件（python-pptx／openpyxl／python-docx）或檔案被鎖時腳本會跳過，改用大小與時間並標 `[推論]`。
   先看這張表，再決定要細看哪幾版，不要逐版讀全文。
3. **專案追蹤檔**：`journal.md`、`progress.md`、`todo.md` 中關於這份成品的決策、客戶回饋、退回原因。

### 3. 逐版歸因
為每一版（或每一段連續小修）填一列：

| 版本 | 時間 | 觸發 | 原因類別 | 可在 v1 前避免？ | 證據 |
|---|---|---|---|---|---|

**原因類別**（可複選，擇主要者）：
- 需求變更：使用者或客戶中途改了要求。
- 需求沒問清楚：v1 前沒確認受眾、用途、範圍、格式，後來才補。
- 理解錯誤：我（Claude）誤解了指示。
- 資料或事實錯誤：數字、來源、圖表有誤，被發現後修。
- 缺資料：中途才拿到資料（或資料在別處）。
- 範圍擴張：做著做著加內容。
- 樣式與格式：版面、字體、對齊、語言版本、品牌風格。
- 審閱回饋：主管、客戶、同事意見。
- 工具或環境：轉檔失敗、檔案被鎖、渲染壞掉。
- 我的疏漏：沒先查證、沒檢查就交付、改一處壞另一處。

**可在 v1 前避免？**：是／部分／否，並寫「要先知道什麼」。這一欄是整份檢討的核心。

### 4. 找模式與根因
- 統計各類別的版數與時間占比，找前 2–3 大。
- 對每個大類寫根因（為什麼會發生，不只是「發生了」），例如：「受眾沒在 v1 前確認 → v3、v7、v12 的口氣與深度重改」。
- 區分「流程可改進」（下次問清楚就好）與「無法預知」（客戶新問題、新資料）。後者不要硬湊規則。
- 依成品類型下結論：交付型 → 給 v1 前檢查清單；調查型 → 給「資料到達時的同步檢查點」（摘要頁、結論頁、數字一致性）與版面基準，不要求減少版本。
- 跨成品比較時，找**共通的重複問題**（例：小字、灰字、圖文重疊、用語不是使用者的），這類最適合升級成規則。
- 若同一版本家族有使用者自己改的版本（使用者說「我更新了報告」或版本時間與其訊息同一分鐘），標為「使用者手動修改」，內容無法歸因時直接寫無法評估，並建議約定主檔或在檔名標示作者。

### 5. 只問缺的
- 證據補不上、又會影響結論的地方，才問使用者。例如：「v9→v13 之間你的修改意見沒留在對話裡，是客戶回饋還是你自己的想法？」
- 一次最多 3–4 題，用 AskUserQuestion，附我目前的假設讓使用者只要確認或更正。
- 缺口很大、或使用者的回答仍含糊（例如「對方不滿意」）時，**呼叫 sharpen 技能**，把已查到的證據與缺口摘要交給它，推敲出更深更細的問題與工作簡報。sharpen 問完，把答案併回證據再往下。

### 6. 產出
檢討報告存成專案 `output/` 下的 `revision-retro_<成品名>_v1.md`（依專案 output 的版本與資料夾規則；專案有「每成品一資料夾」就放該成品資料夾內）。內容：

1. **摘要**（≤8 行）：版本數、時間跨度、前 3 大原因、可避免比例。
2. **逐版歸因表**（步驟 3）。
3. **模式與根因**（步驟 4）。
4. **v1 前檢查清單**：3–7 條，具體可執行（例：「做客戶回覆簡報前，先確認：誰會看、要回答哪幾個問題、哪些數據要原始 log 佐證」）。每條註明對應到哪些版的問題。
5. **建議規則**：可放進專案 claude.md、sharpen 的問題清單、或成品範本的條文。每條標「建議落點」，**不自動寫入**。
6. **未解與無法驗證**：證據不足的部分，以及我推論但沒證據的部分。

回覆使用者：給報告路徑、前 3 大原因各一行、要使用者決定的 1–3 件事（採用哪些規則、落點）。

## 採用規則（使用者同意後才做）
- 專案 claude.md／sharpen／範本：按使用者選的落點修改；改 skill 時依 skill 專案的流程（改來源、打包、驗證）。
- 在專案 journal 記一筆：檢討對象、結論、採用了哪些規則。

## 注意
- Windows：含中文的檔案只用 Edit／Write 寫；Python 輸出設 `PYTHONIOENCODING=utf-8`。
- 對話紀錄包含私人內容：報告只引必要的原話，客戶或個人姓名用角色代稱；不外送。
- 版本檔可能被 Office 開著（有 `~$` 鎖定檔），讀不到就跳過並註明。
- 一次只檢討一份成品（一個版本家族）；多份就分次做。
